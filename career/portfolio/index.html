Overview

I write systems software and I work on language models, and the interesting part is where those two stop being separate jobs. In the last year that has meant an operating system in Rust with a model running inside the kernel, an inference engine that streams weights off an SSD so that a 2.78-trillion-parameter model runs on a laptop, and a year of multi-agent orchestration work that took one company's inference bill down by 89 percent.

Nothing on this page is a plan or a proposal. Every claim below has a repository behind it, and where there is a number it was measured rather than estimated.

GLaDOS

github.com/IlumCI/GLaDOS  ·  a ring-0 operating system in Rust, built around a language model that lives inside the kernel.

GLaDOS is not a Unix. There is no user/kernel split, no syscall boundary, no process isolation and one address space. That sounds like a shortcut and is the opposite of one: it is the arrangement in which a tool call from the model is a function call, with no marshalling and nothing to cross. The model does not sit on top of the operating system. It is a component of it, on the same footing as the scheduler.

Because there is no libc and no Unix to inherit from, everything below the model is also mine:

  • Inference in kernel space. Qwen3-0.6B, int8, referenced in place in the firmware pool rather than copied to the heap, because 570 MB copied twice is 570 MB you do not have. Qwen3.5 hybrids load too, through a separate checkpoint format that carries the layer schedule explicitly instead of inferring it.
  • Cryptography from scratch. TLS 1.3, X25519, ChaCha20-Poly1305, SHA-2, ECDSA over P-256 and P-384, RSA. Primitives were chosen for how checkable they are rather than how fashionable: ChaCha20 over AES-GCM because it has no key-dependent table lookups. Eleven sets of published RFC vectors run at every boot, because this is the one area where writing it yourself is a liability, not a virtue. A broken implementation here produces output that works perfectly and is not secure.
  • A network stack. Ethernet, ARP, IPv4, TCP, UDP, DHCP, DNS, drivers for e1000 and RTL8168, and a WPA2 supplicant verified against the IEEE vectors. The polling layer queues rather than dispatching, because a state machine driven from inside poll can re-enter its own control block while a borrow is still live.
  • Storage. NVMe, and a content-addressed object store where files are named by the SHA-256 of their contents and assembled into Merkle trees, so a copy is O(1) and a snapshot is one hash. Writes are locked by default and every error path re-locks; a safety mechanism you can leave open is decoration.
  • A desktop. Composited window manager, a full pointer, and three applications, drawn to a look borrowed from Windows 98, Windows 3.1 and the sign over the Aperture Science door. The scene is repainted whole and then diffed against a shadow buffer, so correctness is obvious and only changed rows reach the framebuffer.

It is about 40,000 lines of Rust across 93 files. The only code in it that I did not write is Rust's core and 509 hardware initialisation constants for one wireless chipset, transcribed from Linux because no datasheet publishes them, in one file that says so at the top.

Inference on hardware that should not fit it

RustLMHub  ·  if a model fits on the drive, it should run.

An inference and training engine in Rust with nothing underneath it: no PyTorch, no llama.cpp, no CUDA, no BLAS. Feed-forward weights stream from NVMe through O_DIRECT, bypassing the page cache, while attention and embeddings stay resident. On the reference machine, an i7-12650H with 16 GB, that resident set is about 5.7 GB and the rest of the model is on the disk where it belongs.

What is in it, with the measurements that justified each piece:

  • An int8 activation kernel: 2.3 to 2.55× on matmul.
  • Speculative decoding through the model's own multi-token-prediction head, verified in a single forward pass: 1.23 to 1.28× on measured prompts.
  • Certified activation sparsity, skipping up to 27.6 percent of neurons only where the output is provably byte-identical.
  • LUT-GEMM for 4-bit weights on AVX2.
  • Fine-tuning a 27B model on 16 GB by streaming frozen weights and training adapters only.
  • 267 tests, differential and bit-exact against reference implementations.

kimi-k3-in-rust  ·  2.78 trillion parameters on 8 GB of RAM.

Kimi K3's checkpoint is 1.56 TB. Routing activates 16 experts of 896 per layer per token, which leaves 96.3 percent of the weights dormant at any moment, which means they can be on disk behind an LRU cache instead of in memory. The dense trunk is pinned as far as the memory budget allows and streamed beyond it.

The property worth having is not the speed, it is that output is byte-identical from 8 GB to 224 GB. More memory buys seconds per token (26.5 down to 5.6) and buys nothing else. Portable C99, no frameworks, no GPU.

How it gets built

Most of this is written with coding agents driving, and I would rather say so on my own page than have someone work it out. Forty thousand lines of kernel Rust in three weeks is not a typing speed I have. What it does require is knowing what to ask for, reading everything that comes back, and having an answer to the question the agent cannot answer: how would I know if this were wrong?

That question is most of the work, because the failures in this territory are quiet. GLaDOS spent weeks with its rotary position embeddings pairing dimension i with 2i instead of with i + d/2. Both are norm-preserving rotations by the same angles, so there was no NaN, no drift, no error and no crash. The model stayed fluent and simply attended by a scrambled notion of distance, which is indistinguishable from a small model being small. It cost the difference between "The capital of France." and "The capital of France is Paris." Nothing caught it but a numeric oracle in NumPy that the kernel was made to agree with, token by token.

So the practices that matter here are not opinions:

  • Every subsystem has an oracle. The crypto has RFC vectors. The model has a reference implementation in NumPy that reads the same converted checkpoint, so a conversion bug shows up there too and only a kernel bug shows as a mismatch. The tokenizer is diffed against the reference library rather than eyeballed, because a tokenizer that is subtly wrong produces text that still looks like text.
  • Selftests run at boot and print pass or fail per line. There is no host test runner for a UEFI binary, so the boot log is the test suite. An ECDSA break sat visible in it for an entire debugging cycle while I was slicing that output away, which is its own lesson about what "we have tests" is worth.
  • Negative results stay in the tree. Training an adapter head hurt at this data scale. The Product-of-Experts council did not improve accuracy. Both are still there, because the reason to know them is the reason they were worth measuring.
  • Measurement gets designed before it gets trusted. The evaluation harness exists because the measurement was got wrong three separate times: a grid sweep scored on the test set, cross-validation folded by template family, and a test set that moved whenever the corpus was appended to. Three splits now, validation spent freely, the test slice read once.

An agent will happily hand you a confident wrong answer at speed. The job is to build the thing that disagrees with it.
