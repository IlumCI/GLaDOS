TempleOS

What TempleOS got right about single-address-space computing, and how GLaDOS relates to it: lineage, not target.

TempleOS is the obvious ancestor of a project like this, and it is worth being precise about what it shares and what it does not.

What is shared

  • Ring 0, always. No user/kernel split, no syscalls.
  • One address space. Everything can reach everything.
  • No isolation, as a design choice rather than an oversight — with the costs accepted rather than hidden.
  • A deliberate aesthetic. TempleOS committed to 640×480 and 16 colours; this one commits to amber on black and Windows 3.1 chrome.
  • One person, from scratch.

What is not

TempleOS had its own language, HolyC, as the shell and the system language at once. GLaDOS has a small interpreted language, but the system is Rust and stays Rust.

More fundamentally, the organising idea is different. TempleOS was built around a specific personal vision of what a computer should be. This is built around one technical question: what changes when a language model is a kernel primitive instead of a userspace process?

What it got right

That the boundary between kernel and user is a choice, not a law — and that removing it makes some things genuinely simpler rather than merely more dangerous. A function call is a function call. There is no marshalling, no permission check, no context switch, and no ABI to keep stable.

For a system where the model calls kernel functions millions of times, that stops being a philosophical position and becomes an engineering one.

Lineage, not target. This is not an attempt to continue TempleOS, and it is not a tribute to it. It is a different project that happens to have reached some of the same conclusions.
