Tokenizers

Why a byte-pair encoding tokenizer needs the exact pre-tokenizer regex its model trained with, and how the wrong one moved 12% of tokens with no error.

A byte-pair encoding tokenizer has two halves. A merge table, which everyone remembers, and a pre-tokenizer regex that splits text into candidate pieces before any merging happens — which people forget, because it is usually invisible.

The regexes differ, and it matters

GPT-2's pattern and cl100k's pattern disagree in ways that look cosmetic:

  • Under cl100k, a word may be led by any non-alphanumeric character, so (x is one piece rather than two.
  • Digits are emitted one at a time rather than in runs.
  • Punctuation swallows the newlines that follow it.

SmolLM2 trained with the GPT-2 pattern. Qwen3 spells out the cl100k one. Using the wrong pattern moved about 12% of tokens on this project's training corpus — including on the ChatML structure that the instruction tuning depends on.

Twelve percent of nothing visible

There is no error. The tokenizer produces token ids, the model consumes them and emits fluent text. What is actually happening is that the model is being fed sequences it never saw during training, and it degrades gently rather than failing.

So the checkpoint carries which pre-tokenizer it needs as a flag in its header, alongside head width and QK-norm. After the fix, divergence across 407 texts and 66,598 tokens was zero.

Verify against the reference, always

The converter has a --verify mode that reimplements the kernel's algorithm in Python and diffs it against the reference tokenizers library, token for token. It is not optional. A tokenizer that is subtly wrong produces text that still looks like text.

A related trap: sizing the vocabulary from the merge table. Qwen3's 293 special tokens live above it, so the vocabulary was indexed past its end, and the end-of-turn token resolved to id 2 — meaning generation would never stop. Size from the highest added token id, not from the BPE table.
