Content-addressed storage

How GLaDOS stores data: objects named by SHA-256 of their contents, assembled into Merkle trees, so a copy is free and a snapshot is one hash.

The filesystem is not a tree of blocks with names attached. Objects are named by the SHA-256 of their contents and assembled into Merkle trees, which makes several operations collapse to nothing.

  • A copy is O(1) — identical content already has the same name, so copying is adding a reference.
  • A snapshot is one hash — the root of the tree names the entire state.
  • Rolling back branches rather than rewrites — the old root is still valid and still points at everything it did.

The rule that makes it work

The content hash covers content only, and never block locations. This sounds obvious and is easy to violate by including a block pointer in the hashed structure — at which point moving a block to defragment renames the object, every reference breaks, and deduplication silently stops working.

Write locking, and why it stays that way

NVMe writes are locked by default. They unlock only after a target region has been explicitly identified, the formatter re-checks before touching anything, and every error path re-locks.

On a laptop whose disk is fully allocated to Windows there is no such region, and storage initialisation fails. That is the intended outcome, not a bug to work around. Leaving the lock open on failure is exactly how a safety mechanism becomes decorative.

The development machine's boot disk is counterfeit: it advertises 976 GB and holds 14.67. That is why the partitioning tooling uses MBR — a GPT backup header would be written to flash that does not exist — and why it carries an explicit safe-capacity limit.
