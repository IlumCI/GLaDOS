TLS 1.3 from scratch

GLaDOS implements TLS 1.3, X25519, ChaCha20-Poly1305 and ECDSA by hand, validates certificate chains, and is honest about what is still not safe.

The kernel speaks TLS 1.3 using its own implementations of SHA-256/384, HMAC, HKDF, AES, ChaCha20-Poly1305, X25519, RSA and ECDSA. It validates certificate chains against a root bundle exported from the host's store.

This is the one place where writing everything yourself is a liability rather than a virtue. A bug in a driver produces a device that does not work. A bug here produces a connection that works perfectly and is not secure.

Primitives chosen for checkability

The selections are deliberate:

  • ChaCha20-Poly1305 over AES-GCM — no key-dependent table lookups, so no cache-timing side channel to reason about.
  • X25519 over a NIST curve — no point validation required, far fewer ways to be subtly wrong.

Every primitive is verified against published RFC and FIPS test vectors at every boot, and the boot log prints a pass or fail line for each.

An ECDSA break that sat in plain sight

The self-test output is easy to scroll past, and doing so cost an entire debugging cycle: a broken ECDSA implementation was printing FAIL in the crypto block the whole time, while the log was being sliced away to look at something else.

Jacobian coordinates, and a trap

ECDSA uses Jacobian coordinates because affine ones cost a modular inversion per point operation — a full modular exponentiation. For P-384 that meant roughly 460,000 allocating multiplications per signature, which exhausted the heap.

The trap: the inversion routine takes and returns ordinary values, and passing it something already in Montgomery form computes the wrong thing silently. There is a wrapper that does the right conversion, and using it is not optional.

What is still not safe

  • Validation reports rather than enforces — a caller that cares must check the result. This is a known gap.
  • There is no revocation checking of any kind.
  • Key material still comes from the timestamp counter, not RDRAND. That is a real weakness and it is on the list.

Stating these is the point. A system that claimed to be secure here would be worse than one that says exactly where it is not.
