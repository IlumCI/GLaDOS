TLS 1.3 from scratch

This is the one place where writing everything from nothing is a liability rather than a virtue. A bug here produces output that works perfectly and is not secure, and there is no test that distinguishes the two by looking at the result.

Primitives chosen for checkability

ChaCha20 over AES-GCM, because ChaCha has no key-dependent table lookups and can be checked line by line against its specification. X25519 over the NIST curves for key agreement, for the same reason. SHA-256 and SHA-384, HMAC and HKDF, all with published test vectors run at every boot.

Every primitive is checked against published vectors during the boot sequence. That is the entire defence, and it only covers the primitives.

An ECDSA break in plain sight

The signature verification failed its own vector for an entire debugging cycle while the boot output was being sliced down to the section under active work. The break was printed at every boot, in the log, in the section named for it.

It happened a second time on a different subsystem, where a sparsity claim compared a whole file against only the part sparsity can shrink and failed for one commit on an encoding that was working correctly. Both are the same failure of attention, and the instruction that came out of it is to read the whole boot output or to search it for failures across all of it.

Jacobian coordinates, and a trap

Elliptic curve point arithmetic uses Jacobian coordinates. Affine coordinates cost a modular inversion per point operation, which is a full modular exponentiation, and for P-384 that meant around 460,000 allocating multiplications per signature and an exhausted heap.

One trap in that code is worth stating because it is silent. The inversion helper takes and returns ordinary values, so handing it something already in Montgomery form computes the wrong answer with no complaint. There is a wrapper that does the conversion, and the raw function is not the one to call.

What validation actually checks

The chain builds to a trusted root from a bundle exported from the host's store. The transcript signature verifies. Dates are checked. The name is matched against the certificate.

Then it reports. It does not enforce. A caller that cares has to ask the result whether the identity was acceptable, and callers that do not ask get a connection that is encrypted and authenticated against nothing in particular. There is no revocation checking of any kind.

Without the root bundle present, TLS still encrypts and authenticates nothing at all. That is stated in the deployment instructions because it is exactly the sort of thing that looks like it is working.

Key material

Randomness comes from a fast-key-erasure generator built over the same ChaCha20 the boot vectors already check. One block per step, where the first half overwrites the key and only the second half leaves the module, so the state that produced an output is gone before the caller sees it. In a kernel with one address space and no process isolation that is the only route to backtracking resistance.

Two entropy sources feed it, and the second exists because the first has a blind spot. Keyboard and mouse interrupt timing arrive through the same path that decides whether a person is present. Disk completion latency deliberately does not, because disk traffic on an unattended machine would make it look occupied and stand down the loop that only runs when nobody is there.

One bit is credited per event and 256 events are required before a secret will be produced. That figure is an assumption rather than a measurement, and it is the weakest link in the module. The ordinary fill answers below the threshold for anything that wants unpredictability without depending on it; key material takes the strict path, which refuses, because a generator that quietly degrades for a private key is the failure this paragraph exists to warn about.
