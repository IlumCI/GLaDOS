Writing an operating system in Rust

Rust in a kernel is often sold on memory safety, and memory safety is the smaller half of what arrives. The larger half is that the type system can hold invariants which are otherwise comments, and comments in a kernel decay quietly.

What no_std takes away

There is no standard library, so there is no std::io, no threads, no time, no filesystem and no operating system to ask. What remains is core, which is everything that needs no runtime, and alloc, which arrives as soon as a global allocator exists. That allocator is one of the first things the kernel builds, and until it does, every buffer is a fixed array in a static.

Panics need a handler and unwinding is off, so a panic is a print and a halt. There is no backtrace and no symbol table. The panic message is the entire diagnostic, which is a strong argument for putting real information in it.

What ownership buys at ring 0

With no privilege boundary, the compiler is the only thing left that will object to anything. Several invariants in this tree are held by types that would otherwise be discipline:

  • The model engine has one holder. Handing out a second mutable reference to it is undefined behaviour, and two forward passes interleaving in one KV cache produces confident nonsense rather than an error. A claim object records the holder for the length of the work, so nesting is refused by construction. It replaced a pair of flags per task, which is why a third holder went unnoticed for a while: the nightly self-improvement job set neither flag and was handed the engine during its own twenty seconds of work.
  • Capabilities live on the interpreter. There is one interpreter per program, so an import can never be an escalation. The gate is a single allowlist table and a check that runs before dispatch, so a builtin added without a row in the table is unreachable dead code instead of an ungated capability.
  • A sandboxed run records its own changes. The undo path saves each path's pre-image at the moment of mutation, attributed to the task that made it, so a concurrent write by another task is not swept up in the rollback.

Traps that cost real time

Four are worth passing on, because each survived review and was found by a machine.

The calling convention is a lie on this target. On x86_64-unknown-uefi, extern "C" means the Microsoft x64 convention. Anything that must be System V says extern "sysv64" explicitly. Getting that wrong once put a stack pointer inside the framebuffer aperture, and the return instruction popped a black pixel into the instruction pointer.

A guarded match arm placed after the arm it guards is unreachable. The compiler said so in a warning that went unread for several commits.

A debug_assert is checked only in debug builds, and this tree is driven in release. One of them asserted a claim about the wrong dimension and would have panicked on every debug build that attached a Qwen3 adapter. Nothing runs debug under the emulator, so it never fired.

A feature gate must test the feature the code needs. The AVX2 kernel was gated on AVX being enabled and FMA being present, and never on AVX2 itself.

The heap

The kernel heap is one physically contiguous allocation, and its size is a ladder rather than a constant. The memory map on the target laptop cannot be inspected from the machine that builds this, and a fixed size that map cannot satisfy is an unbootable system, so the allocator tries descending sizes, prints the one it got, and says when it had to come down a rung.

Concurrency has the same shape of honesty. The interior mutability wrapper used throughout is named for what it is and its documentation states that it is not a lock. It is single-core interior mutability and the designated grep target for the day that stops being true. Several application processors are started and parked, and they never allocate, never take an interrupt, never print, and never touch anything that wrapper guards. They wait on a generation counter, compute a range of a matrix, and go back to sleep. That is a compute fabric rather than general multiprocessing, and the distinction is the entire reason the safety argument survived.
