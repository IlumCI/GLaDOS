Writing an operating system in Rust

What building a Rust OS actually involves: no_std, a hand-written allocator, the UEFI target, calling-convention traps, and where Rust genuinely helps.

GLaDOS is written in Rust targeting x86_64-unknown-uefi, with no_std and no runtime. This is what that means in practice.

What you give up

no_std removes the standard library, which removes rather more than people expect: no heap until you write an allocator, no File, no Vec until alloc is wired up, no threads, no println!, and no floating-point maths functions — exp, sqrt and tanh live in libm, which is C, which is not there.

For an OS with a transformer in it, that last one is not a detail. Softmax needs exp. So the inference code carries its own.

What you get

Ownership does not stop caring at the hardware boundary. A driver that hands out a buffer it still holds, a ring the allocator might free underneath the controller, a device structure aliased by two code paths — these are compile errors rather than corruption discovered three subsystems later.

The honest caveat: everything touching hardware is unsafe anyway. Rust does not verify that a physical address is mapped, that a DMA buffer is where the device thinks, or that a volatile write hit the register you meant. It narrows the blast radius; it does not remove it.

Traps that cost real time

  • extern "C" on the UEFI target is Microsoft x64, not System V. The context switch has to say extern "sysv64" explicitly, or arguments arrive in the wrong registers and the failure looks like memory corruption.
  • A guarded match arm placed after the arms it guards is unreachable. The compiler warns. The warning went unread for several commits.
  • Interior mutability is not a lock. The type used here is called Racy so that the day SMP arrives, one grep finds every place that assumed one core.

The allocator

The kernel heap is a single physically contiguous allocation chosen from the UEFI memory map, sized by a ladder that steps down until one fits. That matters because the machine's largest contiguous region is not its total RAM — a map can report 1.9 GB free across 84 regions and not have 320 MB in one piece.

A subtle bug lived here: the ladder never degraded, because the probing allocator advanced its cursor destructively, so once the largest rung failed every smaller rung failed too. The fix was a non-consuming largest_span() that looks forward without consuming — rewinding would have handed out the page tables' own frames a second time.
