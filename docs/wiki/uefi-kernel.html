GLaDOS / Wiki / UEFI as the kernel

UEFI as the kernel

The firmware hands control to a UEFI application already in long mode, at privilege level 0, with an identity map covering physical memory and a set of boot services for reading files, allocating pages and drawing on the screen. A conventional kernel throws most of that away and rebuilds it. This one keeps it and simply never leaves.

The build target is x86_64-unknown-uefi. The output is BOOTX64.EFI on a FAT partition. There is no bootloader, no ELF loading, no relocation step and no handoff protocol, because the thing the firmware loads is the thing that runs.

What that deletes

A surprising amount of traditional kernel work simply does not appear. No A20 gate, no protected mode trampoline, no GDT for the transition, no long mode enable sequence, no early page tables written by hand in assembly, no parsing of a multiboot structure. The firmware has done all of it and the first line of Rust runs with the machine already in the state that work exists to reach.

The graphics output protocol supplies a linear framebuffer with a known stride and pixel format, so there is no VGA programming and no mode setting. The simple filesystem protocol reads the model and the tokenizer off the ESP with ordinary calls.

The one-way door

ExitBootServices is the moment the firmware stops helping. After it there is no filesystem, no allocator from the firmware, no console, and no way back. Everything the kernel will ever need from a file has to be read before that line.

That single fact shapes the boot sequence. The model, the tokenizer and the certificate bundle are all read into a pool while services still exist. It is also why the staged update mechanism runs where it does: the firmware's FAT driver is the only writer of the ESP that exists while a boot image can still be replaced, so the update hook runs before the door closes and the swap takes effect at the next boot rather than the current one.

Three real bugs came out of testing that path, and none was reachable any other way. Verifying a signature died on an allocation because the hook runs before the kernel heap is initialised, so there is a static early arena now. The staged image was being read and verified on every boot including trials, which is 2.8 MB and an ECDSA verification to answer a question already settled. And calling ResetSystem through the runtime table while boot services were still up left the machine silent, so the hook stopped rebooting and lets the swap land naturally.

A memory-map trap worth knowing

The obvious way to size an identity map is to take the highest address any memory descriptor mentions. On OVMF that number describes reserved space out to a terabyte. Using it as a map limit exceeds what one page directory pointer table can cover, the identity map silently fails to be installed, and the machine keeps running on the firmware's own tables.

The firmware's tables map page zero. So the null-dereference self-test passed by reading whatever the firmware had left at address zero, and reported success. The check that was supposed to prove faults work was proving that the map had failed.

What the kernel builds for itself

Once the door is shut, the kernel owns its own page tables, its own interrupt descriptor table, its own timer through the local APIC, and its own heap. The heap is a ladder rather than a constant: one physically contiguous allocation, tried at descending sizes, printing which rung it got and saying when it had to come down one. A fixed size the memory map cannot satisfy is an unbootable system, and the laptop cannot be tested from the machine that builds this.

One detail that has cost time twice is worth repeating. On this target, extern "C" is the Microsoft x64 convention. The context switch and every compiled-code entry point are pinned to extern "sysv64" explicitly, and the comment recording what happened when that was got wrong mentions a stack pointer landing inside the framebuffer aperture and a return instruction popping a black pixel into the instruction pointer.
