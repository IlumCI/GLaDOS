GLaDOS / Wiki / Qwen3 in 570 MB

Qwen3-0.6B in a kernel

Qwen3-0.6B at int8 is around 570 MB and is the default checkpoint. Getting it running took two corrections that a working system will not tell you about, because in both cases the broken version loads, runs, stays numerically well behaved and produces fluent text.

Head width is stated

The usual assumption is that a head is the model dimension divided by the head count. Qwen3 states its head dimension separately, and for this checkpoint it is 128 while the derived figure would be 64. The query projection is therefore wider than the residual stream, and the attention path carries more than the stream it reads from.

Assume the derived value and every projection is shaped wrong, every head reads a slice belonging to something else, and the output is still text. The configuration carries the stated width and the file format records it per checkpoint.

QK-Norm

Qwen3 normalises each head's queries and keys before the rotary embedding is applied. Omit it and attention scores come out at the wrong scale, softmax sharpens or flattens accordingly, and the model attends to the wrong things with complete confidence.

Both of these are flags in the header rather than assumptions in the code, because a checkpoint that needs one and a checkpoint that needs neither should both load correctly from the same reader. Version 2 files still load, and their defaults are exactly the Llama ones.

How these get caught

Only by comparison against something known good. A host-side reference implementation reads the same converted file and prints logits for a given token sequence, so a conversion bug appears there too and only a kernel bug shows up as a mismatch. Coherent generated text is the cheap end of the same instrument: a 0.6B instruction-tuned model whose attention path is wired correctly writes real sentences about facts it knows.

The rotary embedding has the same character and has its own page, because it cost the most time of any of them.

Thinking tokens

Qwen3 left alone reasons at length before answering. That is the model working as designed and useless at a 64-token budget, so the block is closed automatically unless the operator asks for it. Whether the model has that mode is decided by asking the tokenizer whether it knows the marker as a single token, which is a property of the vocabulary rather than a guess from a name.

Getting it onto the machine

A conversion tool flattens a safetensors checkpoint into a flat layout the kernel indexes by arithmetic. The context window is set at conversion time and is bounded by the key and value cache rather than by the model: 512 positions costs 112 MiB of kernel heap for this checkpoint, and the tool prints that figure so the decision is made where the window is chosen instead of surfacing as an allocation failure at boot.

The emulator cannot hold this checkpoint through the synthetic FAT path, which is a fixed geometry on a 516 MB disk. A one-shot bootable image sidesteps that entirely and is how any large checkpoint reaches emulation. Saying these models were only runnable on real hardware was wrong on both halves, because the image path existed and the hypervisor accelerator made it fast enough to matter.
