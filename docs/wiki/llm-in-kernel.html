GLaDOS / Wiki / A language model in the kernel

Running a language model inside a kernel

The forward pass is unremarkable arithmetic. Everything around it is where the work is, because at ring 0 with no standard library there is nothing to call.

What is missing

No BLAS. No libm, so exponential, square root, logarithm, sine and cosine are written here and checked against known values at boot. No memory mapping, so the weights are read into a pool while the firmware still has a filesystem and referenced in place afterwards. No allocator during boot until one is built. No threads beyond the cooperative scheduler this kernel runs itself.

Weights are int8 with per-row scales. At 570 MB for Qwen3-0.6B the model is far larger than the rest of the system, and it lives in the pool the firmware handed over rather than on the kernel heap, because copying it would need the heap to be larger than the model.

Where the time goes

Generation is bound by memory bandwidth. The bytes read per token are approximately the size of the model, so 570 MB against 135 MB is roughly 4.4 times the time per token, and arithmetic tuning moves very little next to that.

The classifier is 155 MB of the total. Constrained decoding only ever needs logits for tokens the grammar still permits, so restricting that matrix multiply is the obvious win whenever it matters. The adapter trainer takes exactly that win: it dequantises the reachable rows once, measured at 132 out of 49,152 on one checkpoint, and never reads the int8 classifier again.

Several projections are split across the parked application processors. The split changes no arithmetic, because a row is computed over the same values in the same order whichever core does it, so the self-test compares with exact equality. Any difference at all would be an indexing bug and a tolerance would hide precisely that. Measuring the speedup under emulation does not work and the numbers say so: one core reads 4570 MB/s alone and 3526 MB/s with seven cores merely idling beside it, so both halves of any comparison are contaminated by the host.

A feature gate that tested the wrong feature

The vectorised matrix multiply was selected by checking that AVX was enabled and FMA was present. It never checked AVX2. On a machine with AVX and FMA and no AVX2 that gate admits code the processor cannot run. It was found by reading the gate rather than by a fault, which is the wrong way round and the reason it is written down.

The emulator surfaced a different one. Running under the Windows hypervisor raises unmasked SSE exceptions faithfully where pure emulation hides them, and the first thing that turned up was a genuine bug in the kernel's floating point area allocation.

The general lesson

A model can be wrong without being broken, and that is the failure mode that dominates here. Rotary embedding pairing, query and key normalisation, head width, the normalisation epsilon and the pre-tokenizer regular expression all produce a network that loads, runs, stays numerically well behaved and writes fluent text while attending by a scrambled notion of distance. There is no error to catch.

So the only instruments that settle any of it are a host-side reference implementation reading the same converted file, and generated text that is supposed to contain a known fact. Both are cheap. Neither is optional.
