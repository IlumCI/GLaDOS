GLaDOS / Wiki / How the ISO is built

How the GLaDOS ISO is built

The ISO builder writes both filesystems itself. The practical reason is that xorriso and mkisofs are absent from most Windows machines, and the Windows ADK's equivalent is a 1.5 GB install in order to produce one 600 MB file. Both formats are published, neither is large, and the same reasoning produced the FAT reader in the kernel.

How UEFI boots an optical disc

The firmware reads the El Torito boot catalog, looks for an entry whose platform id is 0xEF, and treats the sectors that entry points at as a FAT filesystem: an EFI System Partition that happens to be living inside an ISO image. It then loads \EFI\BOOT\BOOTX64.EFI from it and jumps.

Which makes the ISO 9660 structure wrapped around the whole thing almost ceremonial: it exists so the disc mounts and shows its contents, not so it boots. It gets built correctly regardless, because a disc that boots fine and appears empty when you mount it looks broken to everyone who checks.

El Torito is named after the Californian restaurant where the specification was drafted in 1994, which is the sort of detail that makes reading old standards worthwhile.

Long file names are not optional

The kernel opens \GLADOS\tokenizer.bin. That base name is nine characters and has no 8.3 representation, so a short-name-only image presents it as TOKENI~1.BIN and the kernel fails to find its tokenizer at boot, on real hardware, at the exact moment there is no filesystem left to debug from, since this all happens after ExitBootServices.

So the builder generates VFAT long-name entries, complete with the specified rotate-and-add checksum that ties each set of long entries to its short entry. Get that checksum wrong and the long names are silently ignored, which returns you to the previous paragraph.

FAT32 has a floor

FAT32 is defined as a volume with at least 65,525 clusters. Below that the volume is by definition FAT16, and firmware that trusts the count over the boot sector's claim will misparse the entire thing. Since the cluster count has a floor, the cluster size sets a minimum image size:

Cluster sizeSmallest possible volume
4 KiB~256 MB
512 B~33 MB

Before this was worked out, the kernel-only image was 269 MB to carry a 1 MB kernel: 255 MB of zeroes, faithfully compressed by nothing and downloaded in full. Choosing the cluster size from the actual payload brings it to 33 MB, and even that is the format's floor: the volume is already as small as a FAT32 volume is permitted to be.

Why write a FAT reader as well

There is a matching FAT implementation inside the kernel, and it exists for a reason that only becomes obvious after ExitBootServices. The firmware can read files, and does; that is how the model gets loaded. But its filesystem driver dies with boot services, so from the moment the kernel owns the machine it can address every block on the disk and understand none of them. That gap is the difference between a system that boots and a system you could use to fix a machine.

FAT specifically, because FAT is what the ESP is, and the ESP is where boot configuration lives and therefore where things go wrong. It is also small enough to implement correctly: a chain of 32-bit numbers, a table of 32-byte records, and one awkward extension for long names.

It is deliberately read-only. Writing FAT means allocating clusters, keeping two copies of the allocation table in agreement, and holding directory entries consistent across a power cut. A rescue tool that can read a broken disk is useful; one that can half-write it is worse than nothing.

Verifying the result

The image is checked by booting it, which sounds circular and is the only test that means anything: firmware is the component least likely to agree with the specification. QEMU with OVMF catches structural mistakes, and the GF63's own firmware catches the rest, of which there have been enough to justify the trip. A disc that boots under OVMF and not on metal is a normal outcome here.
