GLaDOS / Wiki / The network stack

Writing a TCP/IP stack from scratch, ARP to TLS in a kernel

Every layer is hand-written: ARP, IPv4, ICMP, UDP, TCP, DHCP, DNS and TLS 1.3. Drivers exist for Intel e1000, Realtek RTL8168 and USB CDC Ethernet.

The rule that shapes everything

The poll function never dispatches into a transport state machine. It only queues.

The reason is a re-entrancy trap that is easy to walk into. Sending an IPv4 packet calls address resolution; resolution has to poll for the ARP reply while it waits. If polling could run TCP's state machine, a connection could re-enter its own control block while an earlier mutable borrow was still live. So poll queues frames, and TCP and UDP drain their own inboxes from a context where nothing else is borrowed.

No interrupt-driven receive

TCP advances while the shell is idle, or inside a blocking call. This is a deliberate simplification, and it is visible in behaviour: a connection makes no progress while a long generation is running unless the generation yields.

Bugs worth knowing

  • Ethernet pads frames to 60 bytes. A bare 40-byte TCP ACK therefore arrives with 20 bytes of garbage after it. IPv4 payloads must be trimmed to the length the header declares, not to the length the frame happens to be.
  • A shared event ring needs demultiplexing. On the USB driver, waiting for "a transfer event" rather than "a transfer event for my endpoint" meant a send completed against an arriving receive. DHCP still worked, because it alternates send and receive; ARP did not, because it had no send to piggyback on. The asymmetry is what named the bug.

What it can actually do

From the shell: dhcp obtains a lease, ping round-trips, dns example.com resolves, and https example.com / completes a TLS 1.3 handshake, validates the certificate chain against a bundled root store, and returns the page.
