GLaDOS / Wiki / The agent loop

The agent loop

A request becomes an action through the cheapest mechanism that can answer it. The expensive ones are reached only when the cheap ones decline.

Three tiers, spent in order

First the router, which reads one hidden state and answers in about 1.6 ms. Most requests end here.

Second an episode, where the model observes, acts, and observes the result, with the action constrained by a grammar built from the live applet table. Episodes are bounded in steps and in time.

Third a conversation, which is the general case and the most expensive.

The order matters more than any of the individual mechanisms. A system that reaches for the transformer first spends a forward pass on questions a dot product answers.

Skills

A successful episode can be compiled into a program in the system language and kept, so the sequence that worked once can be replayed without the model. That is where the interesting problem starts, because writing a skill used to be the whole of adopting it: the file appeared, the runner would execute it, and nothing had asked whether it was any good.

A candidate is now stored by content address and put through four judges. It has to parse. It has to run under the powers an unadopted skill actually has, which is a real question because a replay of an episode the operator drove often depends on a mutating applet that a sandbox refuses. It has to repeat, giving the same value, the same step count and the same set of touched objects on two runs. And it has to be cheap.

What those judges are is constrained by what a replay skill is. It takes no arguments and dispatches a fixed sequence, so asking whether it generalises to an unseen task is a question it cannot answer, and a judge that could never fail is worse than no judge. These four are admission rather than improvement, and the documentation says so.

One blind spot is written down rather than discovered later: the repeatability judge compares the value, the cost and the objects touched, and does not compare what the program printed. A replay is a sequence of print statements, which answers nothing however the applets behaved.

Who is allowed to be the operator

Every stored program used to run with operator capabilities: raw memory, ports, the network, the model, the framebuffer. Applications had been jailed for a long time and tools had not, and the machine writes tools, and a skill shared by a stranger is a tool. It was open by omission.

Tools now follow applications exactly. Operator powers only for bytes the operator has named by hash, everything else fresh and sandboxed in its own subtree under a step budget. Identity is the hash of the file, so editing a trusted skill revokes its trust by construction. Granting trust is a shell command and never an applet, because a model that could grant itself trust would have defeated the gate by using it.

Prefill made episodes affordable

The conversation resumes its key and value cache instead of resending a transcript. Every chat program re-sends its whole history each turn because the cache belongs to somebody else; here it is ours and it stays, so a turn costs the tokens of that turn and the tenth exchange is as cheap as the first. Measured across two turns, position went from 135 to 150, growing by the new turn alone.

None of that was new machinery. The pieces existed and had simply never been joined up.
