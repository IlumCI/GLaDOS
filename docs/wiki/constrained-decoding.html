Constrained decoding

How GLaDOS guarantees a model can never name a tool that does not exist: a grammar built from the live function table, applied before sampling.

When a language model picks a tool to run, the usual approach is to generate text, parse it, and handle the case where it named something that does not exist. GLaDOS makes that case impossible instead.

The mechanism

At each decoding step the sampler is given only the tokens that could extend the current prefix into a valid name from the live function table. Every other logit is removed before sampling, not checked afterwards.

The consequence is categorical rather than statistical: there is no sequence of sampling outcomes that produces an invalid name. Not unlikely — unreachable. Temperature does not matter. A badly calibrated model does not matter.

Read-only mode is the same mechanism

When the system runs in a read-only trust level, mutating functions are removed from the reachable set before sampling. The model is not asked to behave and then audited; the tokens that spell rm simply have no path.

This is why a script's mutating-ness is derived from its code rather than declared in its header. A script that claims to be read-only and then calls a mutating function would put a mutating entry into the read-only grammar — which is exactly the guarantee leaking. So the system walks the syntax tree, and treats any call whose target is not a literal string as mutating, because a computed name cannot be resolved and guessing would break the property.

How it is tested

The grammar's self-test runs 200 random decodes at maximum temperature and asserts that none escaped the reachable set. It also checks a subtle case: that a name which is a prefix of another name is still reachable — if snap and snaps both exist, a naive implementation makes the shorter one impossible to finish.
