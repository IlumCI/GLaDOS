GLaDOS / Wiki / Tool routing

Tool routing

Choosing which applet a request means is the decision this system makes most often, and it has two implementations. The older and simpler one wins.

The two paths

The first decodes the applet name token by token under a grammar built from the live table. It costs a forward pass plus a token for each piece of the name.

The second reads one hidden state and hands it to a ridge regression solved in the kernel by Cholesky decomposition. Twelve thousand six hundred and seventy two parameters, about 1.6 ms, no transformer forward pass, and better held-out accuracy than the decoder.

The method is Widrow-Hoff, published in 1960. It wins because the task is easy given a good representation, and the transformer's job here is to produce the representation rather than to make the decision.

Why the closed form matters more than the accuracy

A closed-form fit has no learning rate, no epochs, no initialisation and no seed. The same data produces the same classifier every time, which means a routing decision can be re-derived by any later run and a verdict recorded in a ledger still means something a month later.

That property is load-bearing for the self-improvement loop. There is no random seed anywhere in the training path, and the first version of the loop suffered for it in an instructive way: every trial trained a bit-identical adapter with the same content hash, so after the first adoption each later trial was being compared against itself and rejected forever. The fix was a declared grid walked in a fixed order with markers for the points already tried, so the next point is a function of the ledger rather than of a coin.

Agreement rather than votes

Three cores answer: the probe, a hashed n-gram Bayesian classifier, and a lexical matcher. Combining their votes into one answer is the obvious use and it is the less interesting one.

What the ensemble is actually for is confidence. When all three agree the answer is right 90.3% of the time. When they split, 50%. That gap is what the machine acts on when deciding whether to answer, ask, or stand down.

A fourth kind of core can be written by the machine itself: a small program in the system language that reads the text and returns a class. It is judged before it is installed, and it is inert unless the routing rule in force actually consults it, which the machine now says out loud because a core that passes every judge and is never asked anything looks identical in the ledger to a core that is working.

Measurement discipline

This part was got wrong three separate times before it was got right, and all three are recorded because the failures are more useful than the result.

A grid sweep was scored on the test set. Cross-validation was folded by template family in one place and by instance in another. And the test set moved whenever the corpus was appended to, so a figure from last week described a different set of examples.

There are three splits now and exactly one place that answers what they are. Validation is spent freely. The test slice carries a budget, is consulted only after a variant has already won on validation, and prints as stale and unquotable after three reads. A machine that improves itself every night reads the held-out set every night, and the discipline does not survive that unless somebody counts.

Corpora hold out whole template families rather than sampled instances, because instances within a family differ only by slot values, so an instance split measures memorisation while looking like generalisation.
