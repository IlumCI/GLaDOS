# What to run on the GF63, and in what order

**There is no UART on this machine.** The framebuffer is the entire diagnostic
channel, so nothing here can be piped, captured or driven by `drive.py`. Every
command is typed and every answer is read off the screen or photographed.
`todo <text>` writes a note into the machine's own list, which is the hand-off
back to the development host.

The order is deliberate: **everything that can only be measured here comes
first**, and `diag all` comes last, because it can take the machine down (see
the end).

## Deploy

On the development host:

```powershell
.\scripts\deploy.ps1 -EspDrive S: -Release
```

Then reboot and hold **F11**.

## 0. Quiet the machine first

```
initiative off
agent stop
```

The resident mind wakes about fifteen seconds in and holds the engine for a
whole episode. Every timing below is wrong if it fires mid-measurement, and
`initiative off` alone does not cancel the episode already queued.

## 1. The three things QEMU physically cannot answer

These have never executed on any machine. They are first because if the boot
is unstable, these are the measurements worth having.

```
power
battery
ec
```

`power` refuses under a hypervisor by design -- vendor, CPUID and *no
hypervisor*, all three, before any MSR is touched, because an emulator may
advertise a feature and not implement the register behind it. On this machine
all three pass, so the temperature and the delivered-to-reference frequency
ratio are real readings **for the first time**. Under QEMU every battery figure
ever seen was the firmware's fallback branch, not a reading, and the EC's
success path has never run at all: the ports answer `0xFF` and only the timeout
was ever proven.

```
smp
devices
mem
```

`smp` says how many application processors answered -- sixteen logical
processors here against four under emulation. `devices` is the driver registry
against real hardware rather than QEMU's, and its "what is missing" section is
the useful half. `mem` prints the heap ladder rung this machine's memory map
actually allowed and the placeable run below it.

## 2. The parallel numbers, which emulation contaminated

```
smp bench
```

Written to be run here and nowhere else. Under QEMU one core reads 4570 MB/s
alone and 3526 MB/s with seven cores *idling* beside it, so both halves of any
comparison were the host's. This is the first honest figure.

```
mine sweep
mine sweep 16 10000
```

Never run on bare metal. The bare form sweeps to `MAX_SLICES` at five seconds a
point; the second is every slice at ten seconds, which is the one worth
photographing. It installs its own fixture job and puts the coin table back
afterwards, so it needs no pool and disturbs nothing.

**Every sweep figure taken before 2026-09-25 is not comparable to one taken
after, and the reason is that the old ones were measuring the scheduler.**
Slices were `unpin`ned, which makes a task eligible on every core and places it
on none: whether a second core picked one up inside the interval was a race, so
a point could report N slices while fewer than N were hashing, and the shortfall
is indistinguishable from cache contention -- which is the single thing this
curve exists to measure. Slices are placed at spawn now, and each point prints
the cores that actually hashed beside the slices that exist.

Measured on an eight-core host under KVM, same binary either side of the fix:

    slices      1    2    3    4    5    6    7    8
    unpinned  100  202  226  272  314  324  324  381
    placed    100  202  304  401  505  593  697  695

The old shape reads as a machine saturating a little over three slices, and a
constant chosen against it would have been chosen against nothing. The new one
is linear to seven with the eighth flagged `shared 7 core(s)`, which on this
host is honest -- core 0 is left for the shell, so seven is the ceiling. **So
there was no cache contention in that reading at all**, and what the GF63 is
being asked is whether there is any at sixteen. Reproduced within 3% across two
runs; the absolute H/s moved by 1.8x between them with the host's own load, so
read the ratios and never the rates.

## 3. The measurement this session just made under a hypervisor

Under WHPX at four cores, mining doubled the cost of a token and standing down
recovered 48% of that. **This machine has sixteen logical processors and no
hypervisor, so the ratio is the open question**, not the milliseconds.

Six decodes, three conditions, in this order:

```
ask new
ask -n 12 hi
ask new
ask -n 12 hi

mine coin 1 t sha256d
mine slices 4
mine yield off
ask new
ask -n 12 hi
ask new
ask -n 12 hi

mine yield on
ask new
ask -n 12 hi
ask new
ask -n 12 hi

mine yield
mine coin 1 off
```

`ask` prints `N tokens in T s (M ms/token)` each time; those six numbers are the
result. `ask new` before each is not optional -- the conversation resumes its KV
cache, so a second turn is cheaper than the first and the two are not
comparable.

`mine yield` at the end prints how many batches stood down, which is the check
that the mechanism engaged at all rather than the numbers moving for another
reason.

Two samples per condition is thin. If the within-condition pair disagrees by
more than about 10%, take a third: a single sample of this on the development
host put an idle measurement anywhere across a 2x range.

## 4. Graphics, on a real framebuffer

```
video bench
```

Take it twice with identical console contents, because `console redraw_all`
costs what is on screen: the same build measured 497 us after a bare boot and
823 us after `diag all` had filled the scrollback, which reads as a 40%
regression and is a full terminal. `full-screen rect` is the control -- nothing
above the framebuffer can touch it, so what *it* moves by is the noise floor.

```
font
```

The coverage sheet, and the only check that settles a bitmap font. It reaches
the panel, which is the one place a glyph can be judged, and there is no UART
here to print it to anyway.

## 5. Last, because it can end the boot

```
diag all
```

**Do not run it twice in one boot.** `diag paging` followed by `diag smp`
faults -- two worker cores take a `#PF` with a reserved bit set, at an rip in
the AVX2 int8 kernel -- and it needs the sweep run twice to show up. It is
documented in CLAUDE.md, it is not fixed, and it is the reason this is the last
item rather than the first.

If it does fault, the register dump on screen is the whole of the evidence.
Photograph it: the rip and the fifteen registers are what a fix would start
from, and there is no serial log to go back to.

## Writing the results down

```
todo the gf63 numbers: smp bench <x>, mine sweep peak <y> at <n> slices
todo decode: idle <a> ms/tok, mining <b>, yielding <c>
```

`todo` and the ToDo window share one list, and it survives a reboot once a
store is mounted and `snap` has run. It exists precisely because the machine
that builds this is not the machine that runs it.

## None of the above needs a network

Worth stating plainly, because it decides what can be done on a bench with no
cable. Verified under emulation rather than assumed:

    mine coin 1 t sha256d      a fixture coin, generating its own template
    mine slices 2              515869 H/s, best 17 leading zero bits
    mine sweep 4 2000          264975 H/s at one slice, 502301 at two

The sweep says so itself -- "no pool: a fixture job, and a target nothing will
meet" -- and it sets the coin table aside and puts it back afterwards. So the
hash loop, the concurrency curve, the cache budget and the mining-against-model
comparison in section 3 all run offline.

**`mine ev` splits itself at exactly the right place.** Everything it measured
locally is reported; everything that needs a chain is refused:

    hashrate     582198 H/s     measured, 462848 hashes in 795 ms
    sharing      the core with 7 task(s)
    shares       0.488 per hour  derived
    network      no job, so nothing below can be said

Network difficulty, price and revenue against electricity are the half below
that line, and a constant is never substituted for them -- the rule
`src/linux/proc.rs` states about `/proc`, applied to a payout.

## What is still not answered by any of the above

A real `mine pool <host>` run against the deployed pool, which does need a
network. Wired ethernet works today, and so now does a phone: `usb-rndis`
landed after this file was first written, so plugging in an Android handset in
USB tethering mode should bring `eth0` up through the phone's own radio. That
has been driven against QEMU and never against a handset, so it is worth trying
early rather than at the moment the pool run depends on it.
